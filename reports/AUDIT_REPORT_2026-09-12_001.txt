3. HIGH — CLIENT-SIDE ROLES ARE NOT A SECURITY BOUNDARY
--------------------------------------------------------
ID: JULO-SEC-H01
SEVERITY: HIGH architectural blocker for multi-user/cloud use
CURRENT LOCAL-ONLY IMPACT: Limited

Ներկայիս role/permission համակարգը ամբողջությամբ աշխատում է browser-ում։

Workspace state-ը, ներառյալ՝
- members
- role
- projectRoles
- currentUserId

պահվում են localStorage-ում։

Սա նշանակում է, որ browser-ի local user-ը կամ նույն origin-ում script execution ստացած attacker-ը կարող է localStorage-ը փոխելով իրեն Owner/Admin դարձնել, փոխել currentUserId-ը կամ data model-ը։

Այս պահին դա հեռավոր multi-user data breach չի ստեղծում, քանի որ shared backend չկա։ Բայց հենց authentication/backend/sync ավելացվի, CLIENT-SIDE permission checks-ը անվտանգության համար բավարար չեն։

ՊԱՐՏԱԴԻՐ լուծում backend փուլում՝

- իրական authentication
- server-side session/token validation
- յուրաքանչյուր API request-ի server-side authorization
- workspace/project membership checks server-ում
- role changes server-ում
- object ownership/access checks server-ում
- client-ի կողմից ուղարկված role/currentUserId-ին երբեք չվստահել

Այս finding-ը պետք է փակվի մինչև իրական բազմաօգտատեր արտադրական գործարկումը։


4. HIGH — MAIN BRANCH IS NOT PROTECTED
---------------------------------------
ID: JULO-SEC-H02
SEVERITY: HIGH repository / deployment integrity

GitHub branch metadata-ի համաձայն՝

main protected = false
required status checks = off

Repository rulesets list-ը նույնպես դատարկ է։

Միաժամանակ Webapp deploy workflow-ը main-ի webapp փոփոխությունից ավտոմատ deploy է անում GitHub Pages։

Այս կառուցվածքում write access ունեցող account/token-ի compromise-ը կամ պատահական direct push-ը կարող է շատ արագ production-ում հայտնվել՝ առանց PR approval/security gate-ի։

Առաջարկվող minimum protection՝

- Protect `main`
- Require pull request before merging
- Require CI/status checks
- Block force pushes
- Block branch deletion
- Restrict who can push directly
- Prefer required review առնվազն production-ին մոտ փուլում
- Deployment environment protection ըստ անհրաժեշտության

և կարող են commit/push անել main branch։

Հատկապես bootstrap/restructure workflows-ը կառուցված են մեծ source-tree վերագրումների համար և այլևս production runtime-ի համար անհրաժեշտ չեն։ `publish-web-preview.yml` նույնպես redundant է, քանի որ պաշտոնական GitHub Pages deployment-ը արդեն աշխատում է artifact workflow-ով։

Ռիսկը direct unauthenticated exploit չէ, բայց դրանք ավելացնում են repository supply-chain և accidental overwrite attack surface-ը։

Առաջարկություն՝

- Հեռացնել օգտագործված one-shot bootstrap/restructure workflows-ը։
- Հեռացնել `publish-web-preview.yml`, եթե raw.githack fallback այլևս պետք չէ։
- Պահել միայն անհրաժեշտ deployment/testing workflows։


6. MEDIUM — COMMITTED STALE `webapp/dist` CREATES SECOND PUBLIC SURFACE
-----------------------------------------------------------------------
ID: JULO-SEC-M02
SEVERITY: MEDIUM operational/security consistency

`webapp/dist/` repository-ում commit արված build artifact կա, մինչդեռ official GitHub Pages-ը deploy է անում CI-ում նորից build արված artifact-ից։

Այսպիսով գոյություն ունեն երկու տարբեր public code surfaces՝

1) official GitHub Pages current build
2) repository-ում commit արված potentially stale dist (օրինակ՝ raw Git hosting / raw.githack միջոցով)

Stale frontend-ը կարող է չունենալ հետագա bug/security fixes և օգտատերերին շփոթեցնել, թե որն է canonical app-ը։

Առաջարկություն՝

- Official GitHub Pages-ը հայտարարել միակ canonical live build։
- Repository-ից հեռացնել tracked `webapp/dist/` artifact-ը։
- `.gitignore`-ում dist-ը արդեն ignore է արվում, ինչը ճիշտ է։


7. MEDIUM — PLAINTEXT LOCALSTORAGE / ORIGIN ISOLATION
-----------------------------------------------------
ID: JULO-SEC-M03
SEVERITY: MEDIUM confidentiality/integrity

Julo-ն պահում է workspace-ը plaintext JSON տեսքով browser localStorage-ում՝ key՝

julo_web_workspace_v1

Այստեղ կարող են լինել՝
- առաջադրանքներ
- նկարագրություններ
- comments
- member names/emails
- roles/project access

Ռիսկերը՝

- նույն origin-ում XSS ստանալու դեպքում ամբողջ workspace-ը հասանելի է attacker script-ին
- malicious browser extension/local malware/local profile access-ը կարող է կարդալ տվյալները
- backup JSON export-ը նույնպես plaintext է

Հատուկ GitHub Pages origin ռիսկ՝

Julo URL-ը գտնվում է `https://suren-star.github.io/Julo/` origin-ում։ localStorage-ը մեկուսացվում է origin-ով, ոչ թե URL path-ով։ Եթե նույն `suren-star.github.io` origin-ում ապագայում աշխատի այլ Pages application և այն compromise լինի, այդ application-ի JavaScript-ը տեսականորեն կարող է հասնել նույն origin-ի localStorage-ին։

Current account-ի մյուս հայտնաբերված public repository-ում Pages enabled չէ, այնպես որ audit պահին հաստատված sibling Pages exposure չի գտնվել։ Բայց architecture risk-ը մնում է ապագայի համար։

Առաջարկություն՝ զգայուն business data-ից առաջ Julo-ին տալ dedicated origin/custom domain, օրինակ՝ առանձին Julo subdomain/domain։

Նշում՝ IndexedDB տեղափոխելը միայնակ չի լուծում same-origin խնդիրը, քանի որ այն նույնպես origin-scoped է։


8. MEDIUM — NO EXPLICIT CONTENT SECURITY POLICY
-----------------------------------------------
ID: JULO-SEC-M04
SEVERITY: MEDIUM hardening gap

Current production `index.html`-ում չկա Content-Security-Policy meta policy։

Source review-ով current app-ում ակնհայտ XSS sink չի գտնվել, ինչը դրական է։ Բայց CSP-ն defense-in-depth է՝ future XSS/dependency injection impact-ը սահմանափակելու համար։

Static GitHub Pages deployment-ի պայմաններում կարելի է գոնե դիտարկել strict CSP meta tag, օրինակ policy-ն նախագծելով current local assets-ի շուրջ։ Future backend/CDN integrations ավելացնելիս connect-src/img-src/font-src policy-ն պետք է թարմացվի վերահսկված կերպով։

Նաև ստուգել/կիրառել համապատասխան header/meta policy-ներ՝
- Referrer-Policy
- frame embedding protection / CSP frame-ancestors՝ hosting architecture-ի հնարավորությունների դեպքում
- Permissions-Policy՝ եթե տեղափոխվենք custom hosting/proxy-ի վրա


9. MEDIUM — GITHUB ACTIONS SUPPLY-CHAIN HARDENING
-------------------------------------------------
ID: JULO-SEC-M05
SEVERITY: MEDIUM

Deploy workflow-ը օգտագործում է major tags՝

- actions/checkout@v4
- actions/setup-node@v4
- actions/configure-pages@v5
- actions/upload-pages-artifact@v3
- actions/deploy-pages@v4

Սա սովորական պրակտիկա է, բայց high-assurance supply-chain model-ի համար ավելի անվտանգ է immutable commit SHA pinning-ը։

Բացի դրանից, deploy workflow-ի permissions-ը top-level են՝

contents: read
pages: write
id-token: write

Այս պատճառով build job-ը, որտեղ `npm ci` է կատարվում, ստանում է ավելի լայն Pages/OIDC հնարավորություններ, քան միայն compile/test job-ին իրականում անհրաժեշտ է։

Առաջարկություն՝

- Job-level least privilege permissions։
- Build job՝ միայն անհրաժեշտ read permissions։
- Deploy job՝ pages: write + id-token: write։
- Pin critical GitHub Actions-ը immutable SHA-ներով։
- Հին contents:write workflows-ը հեռացնելու դեպքում ընդհանուր attack surface-ը զգալիորեն կնվազի։


10. LOW/MEDIUM — BACKUP IMPORT HAS NO RESOURCE LIMITS
----------------------------------------------------
ID: JULO-SEC-L01
SEVERITY: LOW/MEDIUM local DoS / robustness

Backup import-ը օգտագործում է file.text() + JSON.parse() + normalizeWorkspace()։

Դրական՝
- JSON-ը չի execute արվում։
- eval/new Function չկա։
- fields-ը մեծ մասամբ normalize են արվում։

Բայց չկան հստակ limits՝
- file size
- task/project/member count
- comment count
- string lengths

Շատ մեծ կամ հատուկ պատրաստված backup file-ը կարող է freeze անել tab-ը, օգտագործել մեծ RAM կամ գերազանցել localStorage quota-ն։

Առաջարկություն՝

- Maximum backup file size (օր. մի քանի MB՝ ըստ product requirement-ի)
- Maximum entity counts
- Maximum title/comment/description/tag/email lengths
- Import validation summary մինչ replace անելը
- localStorage QuotaExceededError handling


11. LOW — IDs ARE NOT SECURITY-GRADE IDENTIFIERS
------------------------------------------------
ID: JULO-SEC-L02
SEVERITY: LOW now; important before backend

Current IDs-ը կառուցվում են՝

Date.now() + Math.random()

Սա cryptographically secure չէ և uniqueness-ը 100% երաշխավորված չէ։ Current local SPA-ի համար ընդունելի beta shortcut է, բայց backend/shared system-ի համար ID-ները պետք է ստեղծվեն server-side կամ `crypto.randomUUID()`/database-generated identifiers-ով։

Normalize logic-ը նույնպես duplicate IDs-ի նկատմամբ strict rejection չունի։ Malicious/invalid backup-ը կարող է ստեղծել logical collisions։


12. LOW — NO EXPLICIT SECURITY AUTOMATION IN REPO
-------------------------------------------------
ID: JULO-SEC-L03
SEVERITY: LOW process gap

Current workflows-ում առանձին security automation չի երևում՝ օրինակ՝

- CodeQL / static analysis
- scheduled dependency audit
