2. CURRENT ROLE DEFAULTS

Owner / Սեփականատեր
- Full workspace access (*).
- Manage workspace members.
- Update workspace settings.
- Export workspace.
- Create, rename/update and delete projects.
- Create, update and delete tasks.
- Read tasks.
- Add comments.
- Control timers.
- Reopen completed tasks from done -> doing.

Admin / Ադմինիստրատոր
- Manage workspace members.
- Update workspace settings.
- Export workspace.
- Create, update and delete projects.
- Create, update and delete tasks.
- Read tasks.
- Add comments.
- Control timers.
- Reopen completed tasks from done -> doing.

Member / Անդամ
- Export workspace.
- Create and update projects.
- Create, update and delete tasks.
- Read tasks.
- Add comments.
- Control timers.
- Cannot manage workspace members.
- Cannot reopen completed tasks.

Viewer / Դիտորդ
- Read tasks.
- Add comments.
- Export workspace.
- Cannot edit task fields.
- Cannot control timers.
- Cannot reopen completed tasks.

Guest / Հյուր
- No global workspace permissions.
- Access is project-scoped through project membership.
- Guest Manager: project update + task create/update/delete/read + timer.
- Guest Editor: task create/update/delete/read + timer.
- Guest Viewer: read only.
- Guest roles do not grant task comments.

3. NEW SCOPE STARTING AFTER THIS REPORT

A. Login / registration experience
- Add username-based authentication support in addition to the existing server session model.
- Add Login and Registration pages to the webapp as the first entry experience for backend mode.
- Do not rely on client role claims after login.

B. Development test users
Create an idempotent development/test seed for one workspace with five users:
- owner1 / 12345 -> Owner / Սեփականատեր
- admin1 / 12345 -> Admin / Ադմինիստրատոր
- member1 / 12345 -> Member / Անդամ
- viewer1 / 12345 -> Viewer / Դիտորդ
- guest1 / 12345 -> Guest / Հյուր

Security note:
These short shared passwords are explicitly TEST/DEVELOPMENT ONLY. They must never be provisioned in production. Existing production password policy remains stronger and should not be weakened globally just to support these fixtures.

C. Project management and assignments
- Owner must be able to create, rename/update and delete projects (already authorized; API management endpoints still need implementation).
- Add explicit project team assignment management.
- A new project starts with no explicit assigned team members; workspace Owner/Admin retain their workspace-level authority independently.
- Members/Viewers/Guests can then be assigned to projects according to allowed project/member rules.
- Project assignments must be server-owned and audit logged.

D. Notes / «Հիշեցումներ»
Add a lightweight reminder entity and UI section named «Հիշեցումներ».
Required fields:
- date / ամսաթիվ
- title / վերնագիր
- description / նկարագիր
- label / պիտակ

Behavior:
- Notes are intentionally lighter than tasks and do not require task status, execution type, due date semantics or timer.
- A note can be converted to a task with an explicit action/button.
- Conversion should be transactional: create the task, preserve/link the source note and audit the conversion.
- The conversion flow must request/derive required task-only fields (at minimum execution type and due date) before task creation.
