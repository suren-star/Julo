3. PROJECT TEAM ROLE MODEL CORRECTION
============================================================

The previous Guest-only project-role model was rejected as too restrictive.

The agreed project-team assignment hierarchy is now:

OWNER
- may assign project roles to Admin
- may assign project roles to Member
- may assign project roles to Viewer
- may assign project roles to Guest

ADMIN
- may assign project roles to Member
- may assign project roles to Viewer
- may assign project roles to Guest

MEMBER
- may assign project roles to Viewer
- may assign project roles to Guest

VIEWER
- cannot manage project-team assignments

GUEST
- cannot manage project-team assignments

General rule:
- a role cannot manage a peer or a higher workspace role;
- Owner is the top-level authority and may manage all lower workspace roles.

The rule is enforced in backend authorization as well as UI filtering.

6. PRODUCTION DEPLOY ISSUE — STALE RENDER BACKEND
============================================================

This was the main production incident of the day.

User-visible error in Project Team:
- “Project roles are only used for Guest workspace members.”

Why this error appeared:
- the webapp/frontend had the new project-team hierarchy logic;
- the production Render backend was still running the older d2a858c… version;
- that older backend still enforced the previous Guest-only project-role validation;
- therefore the frontend allowed selecting a role for Admin/Member/Viewer, but the stale backend rejected the request.

This was a frontend/backend deployment-version mismatch, not a new hierarchy-design error.

6.1 Render branch configuration issue
Render service:
- julo-test-api
- service id: srv-daj74vuk1f9s73chchsg

Render was still configured to deploy from:
- backend-auth-foundation

rather than directly from:
- main

The backend-auth-foundation branch was safely fast-forwarded to the new production commit rather than force-rewritten.

6.2 Auto-deploy did not trigger as expected
After the branch was fast-forwarded, Render did not immediately create a new deployment from the updated branch.

At that point Render still showed the previous live deployment:
- commit d2a858c70b6b09392900faf402240ace6c840c63

This explained why the old Guest-only validation remained visible in production.

6.3 Manual deployment resolution
A deploy was triggered through the Render API after confirming the tracked branch pointed to the correct commit.

Final backend deployment:
- commit: 2227c7bea2e72fac5592f251a9ad14273c57122e
- Render deploy id: dep-dajcubp594qs73bna5mg
- trigger: api
- status: LIVE
- started: 2026-09-13T16:28:31Z
- finished: 2026-09-13T16:29:03Z

The prior d2a858c… deployment was then deactivated.

Final verified backend production state:
- project-team hierarchy backend code is LIVE on Render at 2227c7b…

Operational lesson:
- because Render tracks backend-auth-foundation instead of main, merging main alone is not sufficient;
- the tracked branch must be synchronized and the resulting Render deploy must be explicitly verified;
- webhook/auto-deploy should not be assumed successful solely from a GitHub branch update.

Recommended future cleanup:
- reconfigure Render to follow main directly, or define a clearly documented backend release branch and deployment procedure;
- always verify Render deploy commit SHA after backend production changes.
